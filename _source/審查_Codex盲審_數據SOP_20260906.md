### C-01｜位置表沒有「應存在的位置」，整個標記／卡片消失會雙閘同時放行（攻擊面①）

**物證**

- `_source/SOP-數據更新與部署索引.md:12-15` 宣稱 `data-metric` 是位置登記，黑數會被抓出來。
- `_source/deploy-automation/numbers_check.py:165-168,171-208` 只掃「目前還存在」的檔案與標記；`check()` 在 `:211-255` 沒有任何「每個 id 至少出現一次」或「位置／數量不得少於基線」的檢查。
- `_source/deploy-automation/postdeploy.sh:80-90` 又從本地頁面現存標記產生 `ids`，線上只做 `display in text`，不是比對線上的 `data-metric`。
- 實跑無落地模擬：整段標記和數字刪除後，`numbers_check.scan_file()` 回傳 `rows=0, problems=[]`；`postdeploy` 同一算法得到 `expected_ids=[]、bad=0`。
- 更具體地，把線上方法頁 `policy_briefs` 主標記由 `47` 改成 `33`，同頁正文仍有另一個 `47`；現行算法得到 `postdeploy_bad_ids=[]`、`would_accept=True`。對照 `public/methodology/index.html:283-295` 可見主數字與正文重複。

**失效場景**

1. 重構 HTML 時誤刪整張卡、誤刪 `data-metric`，部署前檢查因沒有基線而通過。
2. 線上主數字仍是舊值，但頁面其他文案剛好含新值，部署後只做全文包含判斷，仍印 `LIVE_OK`。
3. `numbers.json` 新增一個 metric、尚未放上任何頁面，也沒有強制失敗。

**修法**

- 建立受版控的預期 manifest（至少 `id + file + selector/穩定位置鍵 + count`）；`numbers_check` 必須檢查 id 零出現、位置消失、數量變少。
- `postdeploy` 直接解析線上 HTML 的 `data-metric`，逐頁比對 `(id, display, count)`；不可用全文 `want in text` 代替。
- 新增三個回歸測試：整卡刪除、標記刪除、同頁正文含新值但主標記仍舊值。

### C-03｜黑數偵測是逐字白名單，不是數值正規化；多種常見寫法實測漏掉（攻擊面②）

**物證**

- `_source/deploy-automation/numbers_check.py:159-162,193-207` 只把 `scan_patterns` 逐字轉 regex；沒有中文數量詞、萬／千換算、全半形或近似語正規化。
- `_source/numbers.json:21,36,66,81` 等處的 patterns 是人工列舉。
- 直接呼叫目前 regex 的結果：

| 寫法 | 結果 |
|---|---|
| `6.6 萬份` | MISS |
| `逾 3,000 篇` | 抓到 `press_coverage` |
| `3,017 篇` | 抓到 `press_coverage` |
| `3,000 篇` | MISS |
| `10 萬人次` | MISS |
| `104000 人次` | 抓到 `single_reach` |
| `逾3千篇` | MISS |

**失效場景**

編輯者把 `66,247` 寫成「6.6 萬」、把 `104,000 人次` 寫成「10 萬人次」、或把「逾 3,000」縮成「3,000 篇」，未加標記仍可通過。更新 metrics 時若把舊 pattern 一併換掉，殘留舊值也可能從掃描面消失。

**修法**

- 先抽取「數字＋量級詞＋單位＋近似前綴」，正規化成數值區間，再與 metric 的 value/display/歷史值比對。
- 至少涵蓋：逗號與全形逗號、有無空白、`萬/千/k`、`約/逾/超過/近`、阿拉伯與全形數字、單位黏連。
- `numbers.json` 保留 `previous_values/previous_patterns`，避免更新後舊頁殘值變成不可見。

### C-07｜IndexNow 兩條路徑都 fail-open；明確失敗仍可得到 `LIVE_OK` 與 exit 0（攻擊面①④）

**物證**

- `_source/indexnow-ping.sh:60-70` 對 400/403/422/429 只印訊息，不 `exit 1`。以 stub curl 回 403 實跑：印出 `❌ Forbidden`，但 `INDEXNOW_HELPER_EXIT=0`。
- `_source/deploy-automation/postdeploy.sh:19,115-136` 沒有 `set -e`，也沒檢查 helper return code；而 `LIVE_OK` 在 IndexNow 呼叫前就印出（`:105-123`）。以本地頁內容 stub、把 helper 指到不存在路徑實跑：顯示 `No such file or directory` 後仍印看板提醒，最後 `POSTDEPLOY_EXIT=0`。
- GitHub 自動路徑同樣在非 200/202 時刻意 `exit 0`（`.github/workflows/indexnow.yml:62-74`）。

**失效場景**

API key 失效、HTTP 403/429、curl 無網路或 helper 路徑壞掉，部署流程仍被記錄成「索引一鍵完成」。

**修法**

- helper 對 curl 錯誤與非 200/202 回非零；postdeploy 用明確 `if ! ...; then` 累計失敗。
- 把狀態拆為 `CONTENT_LIVE_OK`、`INDEXNOW_OK`、`MANUAL_INDEX_PENDING`；只有全部必要項完成才印總體 `POSTDEPLOY_OK`。
- 若產品決策允許 SEO 失敗不擋上線，也必須讓索引工作項失敗並產生待補紀錄，不能以 exit 0 偽裝完成。

## 二、縱深建議（不單獨列 Critical）

1. `_OPEN_WITH_METRIC`（`numbers_check.py:46-47`）只接受雙引號 `data-metric="..."`。改用 HTML parser，並測單引號、屬性換序、HTML entity、全形數字與 meta 單引號。
2. 把「上游清單 → numbers.json → public 投影 → sitemap → postdeploy receipt」做成單一原子變更；PR 缺任一產物即失敗。
3. `numbers.json` 加 schema version、`status`、`approved_by/approved_at`、`previous_values`；避免測試把 `press_coverage` 例外硬編碼在程式。
